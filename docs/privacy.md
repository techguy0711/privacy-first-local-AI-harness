# Privacy: confirmed env vars, and the live egress audit

## Xcode ACP agent: OpenCode rejected, acp-bridge chosen (verified live, 2026-10-06)

Xcode 27 added ACP (Agent Client Protocol) agent support, which requires a locally-running adapter process since ACP agents must implement their own full agentic loop (ACP doesn't proxy raw completions). Two candidates were evaluated for bridging this to our local Ollama model:

**OpenCode — rejected.** Installed it fresh, set every documented privacy flag (`autoupdate: false`, `share: "disabled"`, `enabled_providers: ["ollama"]`), launched it in ACP mode, and watched its connections with `lsof`. Before any client even connects to it, it opens **~26 outbound HTTPS connections**:
- Confirmed via DNS match: `models.opencode.ai` / `api.opencode.ai` (their own cloud — this is not a one-time version check, it happens on every launch)
- The remainder resolve to the same IP range as `registry.npmjs.org` (likely LSP/plugin manifest fetching)

This directly violates "the only allowed outbound traffic is Brave Search API calls" — confirmed by testing, not just by reading GitHub issue reports (which also independently describe this, with no maintainer fix as of Oct 2026: [`opencode#5554`](https://github.com/anomalyco/opencode/issues/5554), [`opencode#16117`](https://github.com/anomalyco/opencode/issues/16117)).

**acp-bridge — chosen.** A small Rust ACP↔local-model adapter ([BlakeHung/acp-bridge](https://github.com/BlakeHung/acp-bridge)), built specifically because servers like Ollama lack a native agentic tool loop. Verified the same way: downloaded the pinned binary, launched it pointed at `coder-local`, and watched its connections for the full lifecycle (startup, a real `initialize` JSON-RPC handshake, idle). The **only** connection it ever opened was loopback — `127.0.0.1->127.0.0.1:11434` (Ollama itself, to list available models). Zero external hosts contacted, at any point. Its README's claim ("zero outbound network calls beyond the configured endpoint... no telemetry, no update checks") held up under live testing.

**Trade-off accepted then**: upstream 0.9.2 has no MCP support and ignores any `mcpServers` the editor offers — a fixed tool set (`read_file`, `write_file`, `edit`, `list_dir`, `search_code`, `bash`, `git_status`/`diff`/`log`/`commit`), so no Brave search and none of Xcode's own tools. Since 2026-10-11 `setup.sh --editors` builds 0.9.2 from source with `editors/acp/acp-bridge.patch`, which adds a small MCP client for exactly those two; the next section covers what that changes. See `docs/editors.md` for registration steps.

## Xcode agent (patched acp-bridge): what can leave the Mac

- **acp-bridge's own traffic stays Brave-only.** acp-bridge itself talks only to the model endpoint and to MCP servers on loopback (`127.0.0.1`, `::1`, `localhost` — checked in code; `HTTP(S)_PROXY`/`ALL_PROXY` are ignored; no redirects off the endpoint's origin). Its one built-in path off the Mac is the guarded `web_search` tool: acp-bridge → the Brave server `stack.sh` starts on `127.0.0.1:8765` (which holds the key) → Brave's Search API, the same path Open WebUI uses. Every query is checked in code before it goes out (refused if it holds code, paths, file names, URLs, key-like strings or names declared in the project; at most 12 words), capped at 3 per turn and 20 per conversation, and logged (`web_search query=...`). acp-bridge's own `web_fetch` stays off (no `LLM_WEB_ALLOWLIST`).
- **Not covered by that: the `bash` tool.** As in upstream acp-bridge, the model's `bash` tool runs any shell command it writes, in the project folder, with no sandbox and no confirmation step (Xcode shows each command as it runs). A `curl`/`wget`, `git clone`/`fetch`/`pull`/`push`, or a package install run there can reach the network and does **not** pass the `web_search` guard — so for the Xcode agent, hard rules 2 and 3 rest on the model following its prompt (which forbids network commands in `bash`), not on code. Watch the commands it runs and press Stop (it kills the running command) if one reaches out. The build-and-fix loop's own builds run offline for Xcode/SwiftPM, Cargo, Gradle and Go projects (`-disableAutomaticPackageResolution`, `--disable-automatic-resolution`, `--offline`, `GOPROXY=off`); for a `package.json` project it runs the project's own `npm run build` script, which can do anything that script does.
- **xcode-tools is a local XPC bridge.** Xcode passes its tool server in `session/new` as `/Applications/Xcode.app/Contents/Developer/usr/bin/mcpbridge` — per static analysis of Xcode 27 (2026-10-09) a stdio↔XPC bridge to the running Xcode with no URL or host strings of its own. acp-bridge starts it only because that canonical path is on its command allowlist (`[mcp] allowed_commands`; any other server an editor passes is ignored) and calls only the curated tools in `[mcp.tools."xcode-tools"] allow`: `DocumentationSearch`, `XcodeRefreshCodeIssuesInFile`, `BuildProject`, `XcodeGlob`. The model sees only `DocumentationSearch` (as `docs_search`), which searches a documentation database installed on the Mac — the query never leaves it. Refused in code whatever the config says: Xcode's Organizer tools that fetch crash and field-performance data from Apple's servers / App Store Connect (IDEAnalyticsKit `GetTopCrashIssues`, `GetCrashIssueLogs`, `GetTopFieldPerformanceIssues`, `GetFieldPerformanceIssueLogs`), `XcodeMessageSend`, and any other open-world tool.
- **BuildProject is Xcode's own build.** When the project's package dependencies changed, Xcode may resolve and fetch Swift packages, and with automatic signing it may contact Apple's developer services for code signing/provisioning — exactly as for a build you start in Xcode. The `xcodebuild` fallback runs with `-disableAutomaticPackageResolution` and `CODE_SIGNING_ALLOWED=NO`, so it neither fetches packages nor signs.
- **Apple analytics.** mcpbridge records a CoreAnalytics event (`com.apple.dt.Xcode.IntelligenceToolUse`: process name, Xcode build, the tool used) per tool use (unless Xcode's own telemetry is off). These stay in macOS's local analytics store and are sent to Apple only while **Share Mac Analytics** is on (System Settings → Privacy & Security → Analytics & Improvements) — keep it off. Xcode's own agent/chat telemetry (`com.apple.dt.Xcode.IntelligencePrompt`, `IntelligenceContentDownloads`, `ChatMessageTelemetry`, per the Xcode 27 binaries) is CoreAnalytics too, so the same switch covers it. `doctor.sh` reads that setting (`AutoSubmit` in `/Library/Application Support/CrashReporter/DiagnosticMessagesHistory.plist`, read-only) and prints a WARN when it's on.
- **Saved conversations stay local.** acp-bridge stores each conversation (history, notes, metadata) under the repo's gitignored `data/acp-bridge/sessions/` so Xcode can resume it (the Android Studio agent uses `data/acp-bridge-android/sessions/`, the same way): dirs `0700`, files `0600`, the values of `LLM_API_KEY`/`BRAVE_API_KEY` and other `*_KEY`/`*_TOKEN`/`*_SECRET` env vars plus common token formats redacted before writing, deleted 30 days after last use. They do contain prompts and the source excerpts the model saw — delete the folder to clear them; `LLM_PERSIST=0` in the agent's env turns saving off.
- **Setup-time traffic** (only when `bin/acp-bridge.stamp` doesn't match the pins, the patches or the installed binary): a `git clone` of `github.com/BlakeHung/acp-bridge` at tag `v0.9.2` (built only if it is the pinned commit) and cargo's crates.io index/crate downloads (exact versions from the upstream `Cargo.lock`, `--locked`), which cargo caches in `~/.cargo/registry` (outside the repo, shared with any other Rust builds on the Mac); with the crates already cached there, the build here fetched nothing (2026-10-11). The Rust toolchain itself (1.86 or newer) is a prerequisite you install with rustup (`sh.rustup.rs`, `static.rust-lang.org`) — `setup.sh` never installs it. The local model pull is now `gemma4:12b` (Ollama's registry, as before).
- **Not yet re-audited live.** The points above come from the patch's code and its tests against mock MCP/Brave servers (non-loopback URLs never contacted, only the fixed Brave arguments sent, refused queries never arriving). A live connection audit of the patched build inside Xcode with a real Brave query, like the 2026-10-06 one below, is still to do.

## Android Studio built-in model providers (partly verified live, 2026-10-15)

The Continue JetBrains plugin was dropped (deprecated and hidden from every JetBrains IDE; see `docs/editors.md`). Android Studio Rabbit 1 | 2026.2.1 now talks to the gateway through its own **Local Provider** (or **Third-Party Remote Provider** in server mode). Method: one second `lsof` samples of Android Studio's TCP connections for 15 minutes, plus Android Studio's `idea.log`/`gemini-backend.log` and Ollama's request log.

- **Model traffic stays local.** Every prompt sent from the Agent tab with `coder-local:latest` selected went to `127.0.0.1:8787` (the gateway) and from there to Ollama. Android Studio first tries `/v1/responses`, gets 404, and falls back to `/v1/chat/completions`.
- **Android Studio's own Google traffic is separate from the model.** It keeps a connection open to Google, fetches server flags and experiment state, and downloads an Android docs index and lint jars from `maven.google.com`. With a Google account signed in to Gemini, it also sent a Gemini `RetrieveUserQuota` request while the Agent tab was in use. None of that carries prompts, but it is outbound traffic this repo can't switch off. Keep **Data Sharing** (usage statistics) off in Android Studio's settings.
- **Its built-in web search is removed (since 2026-10-17).** The agent's `web_search` runs through a Gemini model, not Brave, and the prompt alone didn't stop the local model from calling a tool like it (2 of 3 test runs). The gateway now drops web search tools that aren't Brave-backed from every chat request: the name contains "search" plus "web", "internet", "google" or "bing", and neither the name nor the description mentions Brave. The model never sees the tool, so it can't call it. Documentation and code tools (`search_android_docs`, `fetch_android_docs`, Xcode's `docs_search`, `grep_search`, …) don't match and pass through. Checked through the gateway with the local model and a tool defined like Android Studio's, not yet inside Android Studio.
- **Not verified**: whether `search_android_docs`/`fetch_android_docs` reach Google while a local provider is selected (the test's turn using them ran after the connection sampling had stopped), and whether the local provider works with the Google account signed out.

## Android Studio ACP agent host (code read 2026-10-21/22, not yet audited live)

Android Studio Rabbit 2 | 2026.2.2 runs an external ACP agent ("Bring Your Own Agent", which Google calls a preview). Rabbit 1 | 2026.2.1 has it behind the flag `studiobot.acp.client.enabled`. `docs/editors.md` registers `acp-bridge` there. Method: the host's classes in `plugins/gemini/lib/aiplugin.jar` (`com.google.aiplugin.acp`, `com.google.studiobot.agentsdk.acp`, `…agentsdk.conversations`), read with the bundled `javap`, first in 2026.2.1 and then compared with 2026.2.2 (build `AI-262.10968.63`). There has been no connection audit yet.

- **Agent process**: Android Studio starts the `command` with the `args` and `env` from `acp.json` (`~/.android/studio/agent/acp.json`; it also reads `~/.jetbrains/acp.json` and `~/.acp/acp.json`). The model traffic is acp-bridge's own, so it goes only to `LLM_BASE_URL` (the gateway) and the loopback Brave server.
- **Its agent prompt rides on every message**: for an agent that isn't Claude, Codex or Antigravity, Android Studio prepends its own agent prompt to every message (`PER_TURN_PREFIX`). The prompt holds a persona, tool rules, skills, the project structure and your own rules. It goes only to acp-bridge and from there to the gateway, so it stays on the Mac.
- **Its tools are not used**: Android Studio starts an MCP server on 127.0.0.1 (bearer token) with its agent tools and offers it in `session/new`. With `client_servers = "off"` in `editors/acp/config.android.toml`, acp-bridge ignores it (log: "Ignoring the client's MCP servers"). So none of those tools run, including the Android docs tools whose Google traffic is unverified.
- **Chat titles stay local in 2026.2.2**: Rabbit 2 titles an agent conversation from its first message on the Mac (`AcpConversationImpl.computeFallbackConversationTitle`, no model call). Rabbit 1 instead asked a model for the title (its "Fast" model slot, else the conversation's model), which could have been Gemini. That was never verified there, and it's one more reason to use 2026.2.2.
- **Agent supervisor (new in 2026.2.2), not triggered**: Android Studio sets up a "Fast"-slot model (`AgentSupervisorService`, `OneShotModelRunner`) that judges an external agent's permission requests (`session/request_permission`). If that model is Gemini, those requests (command, file) would go to Google. acp-bridge never sends a permission request (its source has none; it runs its tools itself), so the supervisor never runs for it.
- **Agent registry**: the Agents page downloads `https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json`, the list of installable agents, with no project data. Installing an agent from that list downloads it through `npx`/`uvx`, and those agents talk to their vendors' clouds. Don't install any.
- **Reporting**: no usage-reporting calls were found in the host's own classes. The rest of Android Studio's reporting follows **Data Sharing** (keep it off).

## VS Code agent: the ACP Client extension (source read 2026-10-23, not yet audited live)

Continue is retired: its repository is read-only and 2.0.0 was its last release (`docs/editors.md`). VS Code now runs acp-bridge through an ACP client extension. Two were read on GitHub. **ACP Patchbay** (Apache-2.0, 0.88.3) was rejected: on every window start and every new chat it downloads the agent registry from `cdn.agentclientprotocol.com`, with no setting to stop it (`orchestrator.ts`: `acpRegistry.read("startup")`, `read("new-session")`), which breaks "nothing reports out". **ACP Client** (`formulahendry.acp-client`, MIT, 0.2.0) was chosen:

- **Agent process and model traffic**: the same acp-bridge as the other IDEs (`editors/acp/config.vscode.toml`), started through your login shell with `command`/`args`/`env` from `acp.agents` (arguments shell-quoted). It talks only to `LLM_BASE_URL` and the loopback Brave server. `session/new` carries the first workspace folder and no MCP servers, and the extension's file and terminal capabilities go unused: acp-bridge runs its own tools.
- **No network calls of its own** in the code read: the registry list is fetched only by the **ACP: Browse Agent Registry** command. Its 11 built-in agents start `npx …@latest` packages that talk to their vendors' clouds; the `acp.agents` setup prints replaces that list.
- **Telemetry**: `@vscode/extension-telemetry` (Application Insights) with events such as `extension/activated` (version), `chat/messageSent` (agent name and message length, no text), agent connect/disconnect (agent name, duration, error message) and the shell name. The library follows VS Code's `telemetry.telemetryLevel`, so `"off"` (printed by setup) stops them, and VS Code's own telemetry with them.
- **Local copies**: with `acp.logTraffic` on (its default) every protocol message, prompts, file contents and images included, goes to the **ACP Traffic** output panel; setup prints `"acp.logTraffic": false`. Its chat view sets a `default-src 'none'` content security policy and loads nothing remote.
- **VS Code itself** checks for updates and reaches its Marketplace, as Android Studio contacts Google. With `extensions.autoUpdate` on, a new extension version (unreviewed) installs by itself; turning it off keeps 0.2.0 until you choose to update.
- **The automatic build**: `npm run build` (a `package.json` with a `build` script) runs whatever that script does, and some frameworks send build telemetry by default (Next.js unless `NEXT_TELEMETRY_DISABLED=1`; add it to the agent's `env` for such projects). The other builds run offline (`docs/editors.md`).
- **Installed build checked (2026-10-23)**: `formulahendry.acp-client@0.2.0`, installed from the Marketplace into VS Code 1.141.0. The only hosts in its `dist/extension.js` are Microsoft's telemetry endpoints (`mobile.events.data.microsoft.com`, `dc.services.visualstudio.com` and other Application Insights hosts, from `@vscode/extension-telemetry`, which sends through VS Code's `createTelemetryLogger`, so `telemetry.telemetryLevel: off` gates it), `cdn.agentclientprotocol.com` (fetched only by the registry command), and documentation links. It declares no `untrustedWorkspaces` support, so VS Code runs it only in trusted folders.
- **Not verified yet**: a live connection audit (`lsof`) of VS Code running a session through the extension, like the 2026-10-06 one for acp-bridge.

## Images and files (2026-10-23)

- **Gateway**: chat requests may carry images as inline PNG, JPEG or WebP data URLs in user messages. Each is checked (valid base64, the format's file signature) and passed to Ollama as the bare data URL. GIF (Ollama answers "invalid image input"), image links (http(s), file paths) and other content types (`input_audio`, `file`) are refused, so the gateway never fetches anything. Images have their own budget, `QUEUE_MAX_IMAGE_BYTES` (16 MiB decoded per request; `0` refuses images), on top of `QUEUE_MAX_BODY_BYTES`, and like prompts they stay in RAM only until the request ends.
- **Ollama**: base64 images on `/v1/chat/completions` are in Ollama's OpenAI-compatibility docs (docs.ollama.com, read 2026-10-23); image URLs are not supported there. Checked live through the gateway: `coder-local` read the text and colors of a test screenshot sent as PNG, JPEG and WebP.
- **Open WebUI 0.12.3**: an uploaded image is inlined from Open WebUI's own storage as a data URL (`convert_url_images_to_base64` → `get_image_base64_from_file_id`, owner-checked), with no network. But an `http(s)` image URL inside a message's content, which only Open WebUI's API (not the upload button) produces, is downloaded by the Open WebUI server (`get_image_base64_from_url`, which refuses private addresses) before the gateway sees the request. That is one more user-started outside fetch, like the URL fetch under "Not yet closed" below, and it rests on network egress rules too. Documents (PDF, text, code) are still extracted by Open WebUI on this machine and sent as text.
- **Agents**: acp-bridge advertises image input to Xcode, Android Studio and VS Code (`supports_image = true`); an attached image is stored with the conversation in `data/acp-bridge*/sessions/` (`0600`, deleted after 30 days).
- **Audio stays out of the gateway**: Ollama 0.35 accepts `input_audio` and has `/v1/audio/transcriptions`, but neither is in its OpenAI-compatibility docs, and in a short test clip both heard "nine" as something else ("2:00", "10"). The gateway refuses audio parts. Open WebUI's voice input is transcribed by Open WebUI itself (next section).

## Voice input and spoken replies (2026-10-24)

- **Speech-to-text runs in Open WebUI, on this machine.** The microphone (dictation) and call (voice mode) buttons send the recording to Open WebUI, where faster-whisper 1.2.1 (CTranslate2, CPU, int8) transcribes it with Whisper small from `data/whisper/faster-whisper-small/`. `stack.sh` passes that folder as `WHISPER_MODEL`. Given a folder, faster-whisper loads it without asking the Hugging Face Hub, and `HF_HUB_OFFLINE=1` stays on, so any other model name (Open WebUI's default `base`, or one typed in Admin Settings > Audio) fails instead of downloading. Before this model was installed, that gave "Cannot find an appropriate cached snapshot folder… outgoing traffic has been disabled". The model loads on first use and stays in RAM (about 0.5 GB) until Open WebUI restarts.
- **Setup-time download**: `setup.sh` fetches the 4 files of `huggingface.co/Systran/faster-whisper-small` (OpenAI's Whisper small, MIT, converted by SYSTRAN) at commit `536b066`, with the 483 MB `model.bin` served from Hugging Face's CDN, and checks each against its SHA-256 in `scripts/runtime.sh` before using the folder. `doctor.sh` checks the hashes again. This is the same kind of traffic as Ollama's model pulls, and it happens once.
- **Checked 2026-10-24**: a clip spoken by macOS `say` ("…add nine unit tests…") came back as "add 9 unit tests" in 2.0 s (0.4 s load) on CPU, using Open WebUI's own faster-whisper arguments, with a Python audit hook recording no connection or name lookup outside loopback. The running Open WebUI got `WHISPER_MODEL`, `AUDIO_STT_ENGINE=''` and `HF_HUB_OFFLINE=1` (process environment). **Not verified yet**: a recording made in the browser UI after the change.
- **Recordings are deleted once transcribed.** Open WebUI 0.12.3 keeps each recording (`<id>.wav`, plus the `.mp3` it converts it to) and its transcript (`<id>.json`) in `data/openwebui/cache/audio/transcriptions/` and never deletes them; in server mode that would be every user's voice on the shared box. `stack.sh up` therefore installs `services/voice_cleanup.py` as an Open WebUI event function (Admin Settings > Functions, "Delete voice recordings") and turns it back on if an admin turned it off. Open WebUI runs it after each successful transcription with the recording's ID, and it deletes that recording's files, plus any file in the folder untouched for an hour (a failed transcription publishes no event). `stack.sh` also empties the folder before starting Open WebUI, and `doctor.sh` checks that the function is installed, active and the same as the repo's file. Checked 2026-10-24 in a throwaway Open WebUI 0.12.3 (its own temporary data folder, the real `/api/v1/audio/transcriptions` route): without the function a recording left 3 files, with it none, with no outside connections. Audio files attached to a chat are uploads, not recordings, and are kept like other uploads.
- **Spoken replies use the browser's own voices** (`AUDIO_TTS_ENGINE` empty: the Web Speech API's `speechSynthesis`), so no model is installed for them. Open WebUI lists only the voices the browser marks as on-device (`localService`) unless **Allow non-local voices** is switched on. Chrome's "Google …" voices are network voices that send the reply text to Google.
- **Per-user settings that send data out** (Settings > Audio). These are each user's own, and Open WebUI has no admin switch for them, so they rest on users keeping **Default**:
  - Speech-to-Text Engine **Web API** uses the browser's speech recognition, which in Chrome sends the audio to Google (in Safari, to Apple unless dictation runs on-device).
  - Text-to-Speech Engine **Kokoro.js (Browser)** downloads the Kokoro-82M model and voices from `huggingface.co` into the browser, and its ONNX runtime from `cdn.jsdelivr.net`. Kokoro is not on the allowlist.
  - **Allow non-local voices**, as above.
- **Voice activity detection stays off** (`WHISPER_VAD_FILTER=false`): it would load Silero's VAD model, which ships inside faster-whisper and is not on the allowlist. Since 2026-10-25 `setup.sh` also deletes that model file from the venv (next section).

## Supply chain and audit logs (2026-10-25)

- **The Brave MCP server no longer comes from npm at start.** `stack.sh` used to start it with `npx -y @brave/brave-search-mcp-server@2.1.4`, which contacted `registry.npmjs.org` on every start (1 connection once cached; see the 2026-10-06 audit below) and fetched whatever the package's dependency ranges resolved to on first use. Now `setup.sh` installs it once into `build/brave-mcp/` with `npm ci --ignore-scripts` from `services/brave-mcp/package-lock.json`, which pins all 97 packages to exact versions and sha512 hashes (the same tree the npx cache held), and `stack.sh` runs `node` on it. Checked with `lsof` after `stack.sh up`: the server's only socket was its listener on `127.0.0.1:8765`. At runtime the only outside host is again `api.search.brave.com`, during a search.
- **It no longer sees the other secrets.** The server calls `dotenv.config()` (`dist/config.js`), which reads a `.env` from the working directory, and `stack.sh` started it from the repo, so every value in this repo's `.env` (`WEBUI_SECRET_KEY`, `GATEWAY_SERVICE_KEY`, …) was in its environment; `stack.sh`'s `set -a` exported them to it as well. It now starts in `build/brave-mcp/` with only `PATH`, `HOME`, `BRAVE_API_KEY` and `BRAVE_MCP_ENABLED_TOOLS` (checked with `ps eww`). Nothing suggests it sent them anywhere; this removes the exposure.
- **Silero's VAD model is deleted.** `faster_whisper/assets/silero_vad_v6.onnx` (1.2 MB) was the only model file in Open WebUI's venv after `rapidocr` was left out (a search for `.onnx`, `.safetensors`, `.pt`, `.gguf` and similar). It is outside the allowlist and Open WebUI never loads it with `WHISPER_VAD_FILTER=false` (it calls plain `WhisperModel.transcribe`), so `setup.sh` deletes it after each install and `doctor.sh` fails if it is back.
- **Audit logs (server mode by default).** The gateway writes `logs/gateway-audit.log` and Open WebUI `data/openwebui/audit.log` (`docs/compliance.md`, "Audit logs"). Neither holds prompts, code or replies, but both identify people: account IDs in the gateway's, and names, email addresses and source IPs in Open WebUI's. They stay on the server, owner-only, and are never deleted by the stack; they leave the machine only if an operator forwards them.
- **SBOM.** `setup.sh` writes `build/sbom.cdx.json` (CycloneDX 1.6, `scripts/sbom.py`): every Python package in Open WebUI's venv, the Brave server's npm packages with their sha512, acp-bridge's commit, patches and crates, Ollama's version and each model's digest and license, and the Whisper files' SHA-256. It reads only local files and Ollama's API on loopback.

## Confirmed env vars (verified against current docs and a live run, 2026-10-06)

### Open WebUI privacy/telemetry (set by `stack.sh`, all confirmed current)

Re-checked against the 0.12.3 source and a live staging run on 2026-10-23: every variable below still exists under the same name and does the same thing (see "Open WebUI 0.12.3 upgrade" below).

| Var | Value we set | Effect |
|---|---|---|
| `OFFLINE_MODE` | `true` | disables update checks + automatic model/asset downloads |
| `HF_HUB_OFFLINE` | `1` | blocks Hugging Face Hub network calls |
| `ENABLE_VERSION_UPDATE_CHECK` | `false` | stops the update-check ping |
| `ENABLE_COMMUNITY_SHARING` | `false` | hides/disables community-sharing features |
| `DO_NOT_TRACK` | `true` | standard DNT convention var |
| `SCARF_NO_ANALYTICS` | `true` | disables the Scarf install/runtime analytics pixel |
| `ANONYMIZED_TELEMETRY` | `false` | disables ChromaDB's telemetry |
| `ENABLE_WEB_SEARCH` | `false` | keeps Open WebUI's *built-in* web search off — search goes through the Brave MCP tool instead |
| `TOOL_SERVER_CONNECTIONS` | one MCP connection to `http://$BRAVE_MCP_HOST:$BRAVE_MCP_PORT/mcp`, auth none (`[]` without `BRAVE_API_KEY`) | registers the Brave MCP server as Open WebUI's only tool server, so users don't add it by hand. The key stays in the Brave process; Open WebUI only talks to it on loopback. The entry grants read access to user `*` (`config.access_grants`): since 0.12 a connection without grants is admin-only, and the old `access_control: null` migrates to no grants. Verified 2026-10-23 on 0.12.3: a regular account lists `server:mcp:brave`, and a chat in the UI ran `brave_web_search` and answered with a cited source |
| `ENABLE_USER_WEBHOOKS` | `false` | since 2026-10-23, also 0.12.3's default (`true` in 0.6.31, where any user could set a notification webhook URL and Open WebUI POSTed each reply's title and full text there). 0.12.3 checks it when sending, not only in the UI (`utils/notifications.py`), and offers the model its `notify` tool only while it is on |
| `CORS_ALLOW_ORIGIN` | Open WebUI's own origin(s): `http://$WEBUI_HOST:$WEBUI_PORT`, `http://localhost:$WEBUI_PORT`, plus `https://$SERVER_HOST` in server mode | since 2026-10-23. The default `*` answered credentialed requests from any origin (checked live: `Access-Control-Allow-Origin` echoed a foreign origin with `Allow-Credentials: true`), so a page on another local port, or another internal subdomain in server mode, could read a signed-in user's chats with their `SameSite=Lax` cookie. **Brave Search is on by default in Open WebUI chats with the chat model** (since 2026-10-16). Open WebUI has no env var for default tools, so `stack.sh up` sets the model's Tools setting (`toolIds`) in Open WebUI's database. It creates a private entry if none exists, which keeps the model visible to admins only, as before. With search on, Open WebUI first asks the model whether to search and what to search for, on every message. Unlike the Xcode agent, Open WebUI has no code-level check on that query, so hard rule 3 (no source code in searches) rests on `prompts/system.md` alone. For chats about private code, switch Brave Search off in that chat (the wrench icon in the message box).

**Not yet closed (still so in 0.12.3, 2026-10-23)**: any signed-in user can make the Open WebUI server fetch a public URL (`#` followed by a URL in the message box, `POST /api/v1/retrieval/process/web`, and the YouTube loader). `ENABLE_WEB_SEARCH=false` doesn't gate these, and `ENABLE_LOCAL_WEB_FETCH` (default off; 0.6.31's `ENABLE_RAG_LOCAL_WEB_FETCH` is still read) only blocks private addresses. That is runtime traffic other than Brave that a user starts (the model's own `fetch_url` tool is offered only with web search on), so it rests on network egress rules rather than on this stack's settings.

**Confirmed live** (2026-10-06, before embeddings moved to the gateway): the startup log prints `Embedding model set: nomic-embed-text` and a RAG query's response includes `"embedding_config":"{'engine': 'ollama', 'model': 'nomic-embed-text'}"` — the bundled Hugging Face embedder is never loaded as long as these are set before the first launch.

### Two real bugs found and fixed while testing (not just doc research)

1. **`open-webui serve` ignores `HOST`/`PORT` env vars.** Those env vars only apply to the Docker image's `backend/start.sh` entrypoint. The pip-installed `open-webui serve` command is a separate Click CLI with its own `--host`/`--port` options, **defaulting to `0.0.0.0:8080`** — i.e., without this fix, Open WebUI would have been reachable from the whole network, not just localhost. Confirmed by actually starting it and finding it listening on `*:8080` instead of `127.0.0.1:3000`. Fixed in `stack.sh` by passing `--host "$WEBUI_HOST" --port "$WEBUI_PORT"` as explicit CLI flags.
2. **Open WebUI's internal model id includes a `:latest` tag** that `ollama create coder-<mode>` (no explicit tag) produces, confirmed via `GET /api/models`. `DEFAULT_MODELS=coder-local` silently failed to match; it had to be `coder-local:latest`. Fixed in `stack.sh`.

Both were caught by actually running the stack end-to-end, not just reading docs — a reminder that "the docs say X" and "X is what happens" aren't always the same thing here.

## Open WebUI 0.12.3 upgrade (re-verified live, 2026-10-23)

0.6.31 (September 2025) was replaced by 0.12.3 (16 October 2026), which fixes published advisories affecting 0.6.31, among them CVE-2026-54010 (CVSS 8.3: any signed-in user could read or delete another user's uploaded files). Don't settle on a version from 0.7.0 to 0.11.3: GHSA-vpq8-f445-hcq7 (any website could take a signed-in user's session token, CVSS 8.1) is fixed only in 0.11.4.

**Method**: every setting `stack.sh` relies on was traced in the 0.12.3 source. Outbound traffic was recorded three ways for 18 minutes of startup, API calls, a chat, a 45-chunk document upload and a question about it, a Brave search from the UI, idle time and a restart: a Python audit hook in Open WebUI and the gateway (every socket connect, name lookup and subprocess; for this run uvloop and aiodns were off, so their connections went through Python sockets), `lsof` every 0.5 s on every process of the stack including the Node Brave server, and the browser's list of loaded resources.

**What 0.12.3 changed for this stack**, each handled in `stack.sh`, `setup.sh` or the gateway:
- `GET /api/v1/auths/` answers browser sessions only ("A human session is required." for an API key), so the gateway checks personal keys with `GET /api/v1/users/user/status` (needs `ENABLE_USER_STATUS`, on by default). API keys are off by default (`ENABLE_API_KEYS`, renamed from `ENABLE_API_KEY`) and non-admins also need the `features.api_keys` permission; `stack.sh` turns both on in server mode only. Checked live: a regular account's key works through the gateway, and without the permission the gateway answers 403 "Open WebUI does not allow API keys for this account".
- A tool server without access grants is admin-only, hence the grant in `TOOL_SERVER_CONNECTIONS`.
- Open WebUI embeds a document by sending all its chunks at once (`RAG_EMBEDDING_CONCURRENT_REQUESTS=0`), which the gateway's per-account limit refuses (10 simultaneous requests from one account: 8 got 429). `stack.sh` sets one request at a time, 32 chunks each; the 45-chunk document then embedded in 3 s.
- Open WebUI's model API is async, so `stack.sh`'s default-tools step awaits it.
- `rapidocr`, an open-webui dependency, bundles Baidu's PaddleOCR models (`PP-OCRv6_det/rec`, `ch_ppocr_cls`) and points at `modelscope.cn` for more; 0.6.31 shipped them as well (`rapidocr_onnxruntime`, PP-OCRv4). They only serve OCR of images in PDFs (`PDF_EXTRACT_IMAGES`, off), so `setup.sh` installs Open WebUI without them (hard rule 1) and `doctor.sh` checks. The only other bundled model is Silero's voice activity detector in `faster_whisper`, which stays off (`WHISPER_VAD_FILTER=false`; "Voice input" above) and since 2026-10-25 is deleted by `setup.sh`.

**New in 0.12.3, checked**: the model's built-in `fetch_url` and `search_web` tools exist only with `ENABLE_WEB_SEARCH` on, and `notify` only with user webhooks on; the version check needs `ENABLE_VERSION_UPDATE_CHECK`, the license check a `LICENSE_KEY`; tool and function requirement installs are skipped under `OFFLINE_MODE`; terminals need configured terminal servers (none). `ENABLE_FORWARD_USER_INFO_HEADERS` now also sends the user's name, e-mail, role and chat ID to tool servers, with no per-server switch; the local Brave server doesn't pass them on (its code sends Brave only the query and its own key).

### How to disable each

- Brave search entirely: leave `BRAVE_API_KEY` empty in `.env` — `stack.sh` skips launching the Brave MCP server and `doctor.sh` reports `disabled: no key`. For the Xcode agent alone: `LLM_WEB_SEARCH=off` in its env vars in Xcode.
- The npm registry check on Brave MCP launch: gone since 2026-10-25. `setup.sh` installs the server from `services/brave-mcp/package-lock.json` and `stack.sh` starts it with `node`, so npm is contacted only by that install ("Supply chain and audit logs" above).
- Ollama's registry traffic: only happens during `ollama pull`, which `setup.sh` runs only for a model that isn't installed yet (since 2026-10-14; before that every run checked each manifest with the registry). Re-runs don't contact the registry, so a tag that moves upstream (e.g. a re-published `gemma4:12b`) changes nothing here until you pull it yourself; then rebuild the derived model on it with `ollama create coder-<mode> -f Modelfile.<mode>`.

## Inference gateway

The gateway binds only to loopback (127.0.0.1 and ::1), ignores proxy environment variables and does
not follow upstream redirects. Its destinations are fixed loopback inference and
Open WebUI authentication endpoints; clients cannot select arbitrary URLs or
models. Messages carry text, plus inline PNG, JPEG or WebP images in user
messages; image links and other media are refused and never fetched (see
"Images and files" above).
It also drops web search tools that aren't Brave-backed from chat requests (see the Android Studio section above), so whatever tools an IDE offers, the model can only search through Brave.
The shared privacy/system prompt is added server-side for Ollama, followed by today's date (the gateway machine's local date, computed per request) so the model knows its training data may be out of date.

Job bodies and retained results are in RAM only, never written by the gateway.
Access logging is disabled; backend errors return a generic message rather than
prompt-bearing response bodies. Memory and retention limits are configurable.
WebUI/editor conversation storage still has its own existing retention policy.

Open WebUI forwards user identity only on requests authenticated with its private
service credential. IDE users have personal WebUI keys. The old unauthenticated
embedding proxy is removed. Public TLS and private-network access rules still
apply. No new runtime internet service or model family is enabled.
